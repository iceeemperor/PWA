# 多功能个人效率网站（暂名）设计文档（第二版）

- 日期：2026-11-05
- 状态：第二版，待审阅（审阅通过后才会写实现计划）
- 范围：整个产品的总体设计。实现计划按第 11 节的阶段分别编写，先写阶段 1 和阶段 2。
- 相对第一版的变化见第 15 节。

## 1. 目标与背景

做一个自己每天真正使用的整合工具，取代现在零散的备忘录、日历和表格。

- 手机和电脑都要用，数据自动同步。最差情况下只用手机也要能完整使用，所以**界面手机优先**。
- **好用**排第一，**数据安全**是硬要求：能导出、能备份、不轻易丢。
- 核心模块：待办（含目标和优先级）、日历（含重复事项）、备忘与笔记、日记，另有全局搜索。表格推迟，见 5.5。
- 日历里标为「重要」的事项会自动出现在待办区。
- 设备：iPhone + Windows 电脑，未来有很小的可能买 Mac。

## 2. 已确定的决定

| 事项 | 决定 |
|---|---|
| 形态 | 网页应用（PWA）+ 云端数据库 |
| 使用者 | 只有我自己，不做多人和共享 |
| 云端 | Supabase（Postgres + 登录 + 行级权限）；靠分层保证以后能替换 |
| 同步 | 本机优先；操作队列加服务端 `rev`；冲突由服务器函数在事务内处理 |
| 删除 | 软删除；30 天后服务器清空内容，只保留墓碑 |
| 备份 | 完整 JSON（含回收站）加 Markdown 压缩包；超过 7 天没导出就提醒 |
| 备忘与笔记 | 界面分开，数据放同一张表，用「种类」字段区分，备忘可升级成笔记 |
| 近期计划与目标 | 都放在待办区，目标单独一栏 |
| 待办优先级 | 高、普通、低三档；待办区默认按优先级分组，可切换成纯按日期 |
| 重复事项 | 支持；修改范围只有「仅这一次」和「全部」；作为单独阶段 |
| 搜索 | 在本机数据上做包含匹配；作为单独阶段 |
| 表格 | 推迟，收窄成简单的「记录表」，到时单独设计 |
| 加密 | 第一版不做，只在数据结构上预留字段；密码等敏感内容先不放进去 |
| 原生 iPhone App | 以后有 Mac 再考虑，靠第 4 节的数据规矩保证数据能搬走 |

## 3. 整体架构

### 3.1 前端分层

| 层 | 职责 |
|---|---|
| 界面 | 显示和交互。**只调用本地数据层，不直接调用云端。** |
| 本地数据层 | 统一的读写接口，数据保存在本机 IndexedDB；业务规则（联动、排序、搜索）都在这一层，写成纯 TypeScript 函数 |
| 同步层 | 上传队列、增量下载、冲突结果处理、重试 |
| 云端层 | Supabase：数据库、权限、服务器函数、定时任务 |

以后如果换云端，只改最下面的同步层和云端层。

### 3.2 技术选择

- **前端**：TypeScript + React，用 Vite 构建，做成 PWA（manifest 加 service worker，缓存应用外壳，没网也能打开）。
- **托管**：静态托管，首选 Cloudflare Pages，备选 GitHub Pages。手机和电脑打开同一个网址。
- **云端**：Supabase。**数据库的所有变化都写成版本化的 SQL migration，用 Supabase CLI 管理**，不手动修改线上数据库。
- **本机数据库**：IndexedDB。它是工作副本，不是唯一备份（见第 8 节）。

### 3.3 云端安全要求

- 所有表启用行级权限（RLS）。SELECT、INSERT、UPDATE、DELETE 的策略分别单独写。
- INSERT 和 UPDATE 的策略都带 `WITH CHECK (user_id = auth.uid())`，保证新行仍属于当前用户。
- `rev` 和 `updated_at` 由数据库触发器写入，客户端传来的值一律无效（只有导入函数能保留 `updated_at`，见 7.2）。
- 前端只持有公开的 anon key，**service_role 密钥绝不进前端、不进仓库**。
- 登录用邮箱加密码。创建好自己的账号后，在 Auth 设置里**关闭新用户注册**，并且不启用匿名登录和第三方登录，确认没有其他公开创建用户的途径。

### 3.4 Markdown 渲染

支持 CommonMark 加任务清单（可点击的勾选框）。**禁止原始 HTML**，渲染前必须净化，防止导入的文件或冲突副本里的内容被执行。

### 3.5 界面

最小宽度 360px。手机用底部导航，宽度 768px 以上用侧边导航。先把 iPhone 上的操作流畅度做好，Windows 端再利用大屏幕。各模块的具体界面在对应阶段的实现计划里确定。

## 4. 数据规矩

所有数据表都有这些公共字段：

| 字段 | 说明 |
|---|---|
| `id` | UUID v4，由前端生成（离线也能新建），不用自增数字，是主键 |
| `user_id` | 所属用户，行级权限依据，建索引 |
| `created_at` | 创建时间，UTC。由客户端在创建时写入，只用于显示和排序，不参与同步判断，创建后不再修改 |
| `updated_at` | 修改时间，UTC，**只用于显示**，由服务器写入（导入函数除外） |
| `rev` | 修改序号，bigint，**由服务器写入**：所有表共用一个序列，每次新增或修改都取序列的下一个值。它同时承担两个作用：冲突判定（提交时必须等于我上次看到的值）和增量拉取的游标 |
| `deleted_at` | 为空表示正常，有值表示在回收站 |
| `purged_at` | 为空表示内容完整；有值表示内容已被服务器清空，这一行只剩墓碑 |

其他规矩：

- `(user_id, rev)` 建索引，用于增量拉取。
- 时间戳（`created_at`、`updated_at`、`deleted_at`）一律用 ISO 8601、UTC。日记和待办的日期是不带时区的 `YYYY-MM-DD`。**日历事项是例外**，用「本地时间加时区名」，见 5.1。
- 删除只是写入 `deleted_at`。30 天后由服务器清空内容、写入 `purged_at`，这一行**永远保留**（墓碑），这样任何离线再久的设备回来，都能通过拉取知道它已被删除。
- 子记录（重复事项的单次例外、以后的表格行）的显示、删除和清理都跟随父记录：父记录进回收站，子记录就不显示；父记录被清空，子记录一起被清空。
- 笔记、备忘、日记的正文就是纯 Markdown 文本，不存成专用格式。
- 导出文件带版本号（第 7 节）。

这些规矩是为了以后换同步系统或迁到原生 App 时数据能搬走。

## 5. 模块与数据

### 5.1 日历事项 `events`

| 字段 | 说明 |
|---|---|
| `title` | 标题，必填 |
| `all_day` | 是否全天 |
| `starts_at` / `ends_at` | 全天事项为 `YYYY-MM-DD`；非全天为本地时间 `YYYY-MM-DDTHH:mm`（不带偏移）；`ends_at` 可为空 |
| `tz` | IANA 时区名，如 `Asia/Shanghai`；全天事项为空 |
| `note` | 备注，纯文本 |
| `important` | 是否重要，默认否 |
| `done` | 是否完成，默认否；只用于不重复的事项 |
| `rrule` | 重复规则，可为空，空表示不重复 |

- 非全天事项存「本地时间加时区名」，不存 UTC，这样每周九点的事项在夏令时变化后仍是九点。界面显示和判断「今天」时，再换算成设备所在时区。
- **重复规则**用 RFC 5545 的 `RRULE` 格式的一个子集：`FREQ`（`DAILY`、`WEEKLY`、`MONTHLY`、`YEARLY`）、`INTERVAL`、`BYDAY`（只用于每周，如 `MO,WE`）、`BYMONTHDAY`（只用于每月）、`UNTIL` 或 `COUNT`（最多二选一，都没有表示永不结束）。第一版不支持「每月第二个周二」这类规则，也不支持多条规则。每月 29、30、31 日的事项，在没有这一天的月份会跳过（`RRULE` 的标准行为）。
- 界面按可见的日期范围，在客户端展开出每一次，使用成熟的 `rrule` 库，不自己实现。
- 重复事项自己的 `done` 不使用，每一次的完成状态存在 5.1.1 的单次例外里。
- 界面：月视图加当天列表。有日记的日期显示小标记，点击跳到当天日记。重要且已完成的事项在日历上显示为划线。
- `tz` 和 `rrule` 两列从第一次建表就存在；第一版（阶段 2）里 `rrule` 始终为空，界面不开放。

#### 5.1.1 单次例外 `event_overrides`（阶段 3 建表）

| 字段 | 说明 |
|---|---|
| `event_id` | 所属重复事项 |
| `occurrence_date` | 这一次**原本**所在的日期，`YYYY-MM-DD`，按事项的 `tz` 计算 |
| `done` | 这一次是否完成 |
| `cancelled` | 这一次是否被删除 |
| `title`、`starts_at`、`ends_at`、`note` | 可为空；有值表示仅这一次改成这样 |

`(event_id, occurrence_date)` 在未删除的记录里唯一。

- 「仅这一次」修改：写入或更新这一条例外。「仅这一次」删除：`cancelled = true`。「全部」修改：修改事项本身，已有的例外保留；如果改动让某条例外的日期不再对应任何一次，这条例外被忽略（不显示），直到事项被清理。
- 勾选重要重复事项的某一次，写入这条例外的 `done`。
- 两台设备离线各给同一次创建例外，推送时后到者覆盖已有那条的字段，不留副本（例外里没有长文本）。
- 不支持「这次及以后」。需要时手动结束旧事项、新建一个。

### 5.2 待办与目标 `todos`

| 字段 | 说明 |
|---|---|
| `kind` | `todo` 或 `goal` |
| `title` | 标题，必填 |
| `done` | 是否完成 |
| `priority` | `high`、`normal`、`low`，默认 `normal`；目标不使用 |
| `due_date` | `YYYY-MM-DD`，可为空；目标不使用 |
| `note` | 备注，Markdown |
| `steps` | 小步骤数组 `[{id, text, done}]`，只有目标在界面上使用 |

### 5.3 备忘与笔记 `notes`

| 字段 | 说明 |
|---|---|
| `kind` | `memo` 或 `note` |
| `title` | 标题，可为空；备忘不显示标题输入 |
| `body` | Markdown 正文 |
| `checklist` | 勾选清单 `[{id, text, done}]`，可为空 |
| `color` | 卡片颜色，可为空 |
| `pinned` | 是否置顶 |
| `labels` | 标签，文本数组 |
| `archived` | 是否归档 |
| `origin` | 可为空。冲突副本用它记录来源：`{source_table, source_id, source_label, overwritten_at}`，其中 `source_label` 是原标题或日期，`overwritten_at` 是被覆盖的时间 |
| `encrypted` | 预留，默认 false，第一版不使用 |
| `crypto` | 预留，JSON，可为空，第一版不使用 |

界面：

- **备忘**是快速记一句话的小卡片。页面顶部常驻一个输入框，输入后回车就保存。点击卡片复制内容。可设颜色和置顶。
- **笔记**是长篇 Markdown 文档，列表加编辑页。
- 备忘可一键升级成笔记，就是把 `kind` 改成 `note`。

### 5.4 日记 `journal`

| 字段 | 说明 |
|---|---|
| `date` | `YYYY-MM-DD` |
| `body` | Markdown 正文 |
| `encrypted` / `crypto` | 预留，同 5.3，第一版不使用 |

- **数据库用部分唯一索引保证每天最多一篇**：`UNIQUE (user_id, date) WHERE deleted_at IS NULL`。
- 两台设备离线各写了同一天的日记，第二台推送时会撞上这个索引。处理方式是**自动合并**：服务器把后到的正文接在已有正文后面，中间加一条分隔线，不丢内容，仍然是一天一篇。第二台设备随后收到合并后的那一篇，并丢弃自己本地那条。
- 从回收站恢复日记时，如果该日期已经有新日记，则拒绝恢复并提示；旧内容仍可在回收站里查看和复制。

### 5.5 表格（推迟）

表格推迟到阶段 7，并且收窄成简单的「记录表」，用来记录数据，不追求 Excel 的功能，也不做公式。它的数据结构、删除和级联规则、列和行的排序规则，到那时单独走一遍设计和计划。**在那之前不建表。**

## 6. 日历与待办的联动

待办区是一个**合并视图**，不复制数据。

### 6.1 「近期」栏

由三部分合并：`kind = todo` 的待办、`important = true` 的日历事项、重要重复事项展开出的每一次。

- 日历事项的日期是它在设备时区下的开始日期；全天事项取它自己的日期。「今天」以设备本地时区为准。
- 显示未完成的项目，条件是：日期不晚于今天之后 14 天，或者是没有日期的待办。
- 重要重复事项**只显示从今天起的每一次**，不产生「过期未完成」，避免每天重复的事项越积越多。
- 已完成的项目默认隐藏，打开「显示已完成」开关后全部显示，按日期倒序。

### 6.2 排序

有两种模式，用一个按钮切换，选择保存在本机，不同步。

**按优先级（默认）**：先分三组，高、普通、低。重要日历事项（含重复事项的每一次）算「高」。每组内：已过期未完成的最前，按日期从早到晚；然后是今天及以后的，按日期从早到晚；最后是没有日期的待办，按创建时间从新到旧。已过期的项目带红色标记。日期和优先级都相同时，按 `id` 排，保证顺序稳定。

**按日期**：不分组，规则同上，只是忽略优先级。

### 6.3 勾选与跳转

- 勾选待办写入 `todos.done`；勾选不重复的日历事项写入 `events.done`；勾选重复事项的某一次写入对应例外的 `done`。数据始终只有一份。
- 来自日历的项目带日历标记，点击可跳到日历当天。

### 6.4 「目标」栏

单独显示 `kind = goal` 的项目，不受 14 天范围限制，不出现在日历上，不参与优先级排序。目标可以加小步骤，勾选步骤写入 `steps`。

## 7. 导出与导入

### 7.1 导出

**完整备份 JSON**（灾难恢复和迁移用）：

```json
{
  "format": "productivity-app-export",
  "version": 1,
  "exported_at": "2026-11-05T00:00:00Z",
  "tables": {
    "events": [], "event_overrides": [], "todos": [],
    "notes": [], "journal": []
  }
}
```

- 包含所有记录，**包括回收站里的**（带 `deleted_at`），但不包含已被清空的墓碑。尚未建表的类型（例如阶段 3 之前的 `event_overrides`）导出为空数组。
- 每条记录带全部字段，只去掉服务器管理的 `user_id`、`rev`、`purged_at`。
- 第一版不存图片和附件，文件里只有文字，体积很小。将来加附件时，附件另外打包，不塞进 JSON。

**Markdown 压缩包**（只用于阅读和迁到别的软件，不用于导入），在浏览器里生成：

- `notes/` 下每篇笔记一个 `.md` 文件，开头带 front matter（id、创建时间、标签、置顶、颜色）。
- `journal/` 下每天一个 `YYYY-MM-DD.md`。
- 所有备忘合并在一个 `memos.md` 里，每条一行。
- 只包含正常内容，不含回收站。
- 导出时可以选范围：全部，或者**只导出日记**，方便单独把日记备份到网盘。

**保存位置**：Windows 上走浏览器下载，可把下载位置设成 iCloud 文件夹；iPhone 上通过系统分享面板保存到「文件」里的 iCloud 云盘（不可用时退回普通下载）。

**导出提醒**：距离上次导出超过 7 天，在首页和设置页提示。上次导出时间记在本机。

### 7.2 导入

导入当成**恢复**，不是合并。

1. **整体校验**：`format` 必须匹配，`version` 必须是已支持的版本；每张表的每条记录要符合字段类型和必填项，`id` 必须是合法 UUID；引用关系必须成立（例如 `event_overrides.event_id` 必须指向文件里或云端已有的事项）。**只要有一处不通过，整个文件被拒绝，不写入任何数据**，并列出前若干条错误。
2. **写入**：通过一个专用的服务器函数完成，它是唯一允许保留文件里 `updated_at` 的途径（函数在事务内设置一个只对本事务有效的标记，触发器看到标记就不改写 `updated_at`），`rev` 仍由服务器分配。
3. 云端不存在的 `id`：新增，`deleted_at` 照原样保留，回收站里的记录导入后仍在回收站。
4. 云端已存在且内容完整的 `id`：**跳过，不覆盖**。
5. 云端已存在但已被清空的 `id`（墓碑）：默认**跳过**，因为那是你主动删除、又过了 30 天的数据，备份不应该悄悄让它复活。导入界面有一个选项「同时找回已被永久清除的记录」，**默认关闭**。打开后，墓碑会被文件里的内容还原：服务器清除 `purged_at`，写回内容，分配新的 `rev`（其他设备拉取时会收到还原后的内容）。细节：
   - 父记录先于子记录还原。
   - 如果文件里这条记录处于回收站，`deleted_at` 重置为导入的时刻，否则下一次清理会立刻把它再清空。
   - 日记的日期如果已被另一篇有效日记占用，这条跳过，并在结果里列出。
6. 没打开找回选项时，父记录仍是墓碑的子记录也跳过。完成后显示新增、找回、跳过各多少条，跳过的按原因分组。
7. 整个云端库丢失的情况下（没有任何墓碑），所有记录都会作为新增恢复，不需要打开找回选项。

## 8. 同步与出错处理

### 8.1 流程

**本机优先**：所有写入先经本地数据层写入 IndexedDB 并立即显示，同时把一条操作加入上传队列。

- **推送**：同步层按顺序把队列里的操作推给服务器。每条操作带一个唯一的 `op_id`、目标表、`id`、`base_rev`（我上次看到的 `rev`）和改动的字段。**只带被改的字段，不是整条记录，服务器只覆盖这些字段**，所以一台设备改完成状态、另一台改标题，两个改动都会保留。**推送从不使用 upsert。**
- **拉取**：向服务器取 `rev` 大于游标的记录，分页取完。拉取时从游标往回退 100 再取，重复的记录按幂等规则忽略：只有收到的 `rev` 比本机那条更大才应用。这样并发事务的提交顺序不会造成漏拉。
- 游标和数据保存在同一个 IndexedDB 里，在同一个事务里更新，一起丢、一起重建。IndexedDB 里有一个 `db_id`，缺少它就当作全新安装：游标归零，完整下载一遍。
- **本机数据库为空，从不被解释成「全都删了」。** 删除只来自明确的删除操作和拉到的墓碑。所以用户清除浏览器数据后重新打开，只会触发一次完整下载，云端不受影响。
- 触发时机：应用打开、回到前台、每次本机写入后。写入后立即推送，对连续输入做 2 秒防抖，不攒批。第一版不做实时推送。

### 8.2 服务器如何处理一条推送

推送由一个对所有表通用的服务器函数（`push_change`）处理，在一个事务里完成：锁住目标行，判断，写入，必要时写冲突副本。

- **重复推送**：服务器记录已处理的 `op_id`（存在内部表 `applied_ops` 里）。同一个 `op_id` 再次到达，直接返回上次的结果。这是为了在「服务器已提交但响应丢了」时，客户端重试不会被误判成冲突。
- **新增**：直接插入。例外：日记同一天已有时按 5.4 合并；重复事项例外同一次已有时按 5.1.1 覆盖；`id` 已经存在时（例如旧的 `op_id` 记录已被清理后又收到重发）不插入第二条，按修改处理。
- **修改，且 `base_rev` 等于当前 `rev`**：直接应用。
- **修改，但 `base_rev` 不等于当前 `rev`**（另一台设备改过）：仍然应用，**最后被服务器接受的修改为准**，不看设备本地时间。如果被覆盖的字段是笔记的 `title`、`body`、`checklist`，或日记的 `body`，并且旧值与新值不同，就在**同一个事务里**把被覆盖的旧内容存成一条冲突副本：新建一条 `kind = note` 的笔记，标题为「冲突副本」加原标题（日记用日期）和时间，正文是被覆盖的旧内容，`origin` 记录来源。副本是新 `id` 的普通插入，不会再触发冲突判断。这个判断偏保守，宁可多留一份无害的副本，也不丢内容。其他类型和其他字段不留副本。
- **删除**：始终应用，不看 `base_rev`。被删除的那一版内容就在回收站里。
- **被操作的记录已在回收站**：只有「恢复」操作会被应用；其他修改不应用，笔记和日记的这次修改内容存成冲突副本，其他类型丢弃。
- **被操作的记录已被清空（墓碑）**：任何操作都不应用，处理同上，并且不能恢复，界面提示「已被永久清除」。
- 函数返回这条记录的最新状态和 `rev`。客户端更新本机副本，冲突副本在下一次拉取时到达。同步后如果出现冲突，界面提示「同步时发现 N 处冲突，已保存冲突副本」，并能点进去。

### 8.3 离线与本机存储

- 没网时，改动留在上传队列，界面显示「未同步」和待上传的数量，网络恢复后自动补传。
- **队列非空时界面要有明显提示**，因为 iPhone 可能清理长期不用的网页存储，未上传的队列是那一刻唯一的一份数据。
- 启动时申请持久化存储（`navigator.storage.persist()`）。iPhone 是否批准取决于系统，不能当作保证。
- 清除浏览器数据会丢掉尚未上传的队列。这是平台限制，靠「写入后立即同步」和上面的提示把风险降到最低。

### 8.4 出错的分类

| 情况 | 处理 |
|---|---|
| **保存失败**（本机写入失败，如存储空间不足） | 立刻提示，不加入队列 |
| **同步失败：网络问题** | 自动重试，间隔逐渐拉长，界面显示「未同步」 |
| **同步失败：服务器拒绝**（数据不合法） | 不再自动重试，放进「同步失败」列表，等用户处理 |
| **登录失败或会话过期** | 明确提示并回到登录页，本机未上传的改动保留，重新登录后继续上传 |
| **云端暂时不可用**（例如免费项目被暂停） | 提示「云端暂时无法连接」，本机数据不受影响，所有操作继续留在队列里 |

### 8.5 回收站与清理

- 删除进回收站，30 天内可恢复。回收站界面放在设置里，按类型列出，可恢复。已被清空的不列出。这个界面在阶段 2 做，之后每个模块完成时接进去。
- **服务器每天运行一次清理**：把 `deleted_at` 早于 30 天的记录清空内容、写入 `purged_at`、并更新 `rev`（让各设备拉到墓碑）；其子记录一起清空；同时删掉超过 30 天的 `applied_ops`。
- 清理用 Supabase Cron 定时运行。官方文档确认它能按天运行 SQL，但没写明免费版是否可用，**实现阶段 1 的数据库步骤时要实际验证**。如果不可用，改成应用启动时调用一个服务器函数，由函数自己判断清理哪些数据，客户端不传参数。

## 9. 全局搜索

- **在本机数据上搜**，不走服务器：速度快，离线可用，以后做加密时也只有本机能搜到解密后的内容。
- 范围：待办、目标（含小步骤）、日历事项（标题和备注）、备忘、笔记、日记。**不搜回收站。**
- 匹配方式：把搜索词和被搜内容都做 Unicode NFKC 规范化（统一全角半角）并转小写，搜索词按空白分成多个词，**每个词都必须作为子串出现**。中文没有空格分词，用子串包含比分词库更适合；个人数据量下是瞬间的，不建索引。
- 结果按模块分组，组内按 `updated_at` 从新到旧，显示命中的片段并高亮，点击跳到对应项目。
- 入口是顶部的搜索框。数据层提供 `search(query, options)` 接口，阶段 1 先定好接口形状，阶段 6 实现。

## 10. 加密预留

第一版不做加密。`notes` 和 `journal` 已预留 `encrypted` 和 `crypto` 字段，以后加密时不需要改表结构。

- `crypto` 保持可扩展，预留算法版本、密钥派生参数、随机数和密钥标识的位置，不把格式定死。
- 预期做法是在设备上加密正文，云端只存密文，用浏览器自带的标准加密（Web Crypto 的 AES-GCM）。但 AES-GCM 只解决内容加密，真正做的时候还要回答：密钥怎么从密码派生、盐值存哪里、能不能改密码、多台设备如何获得同一个解密能力、忘记密码怎么办、加密格式如何升级。这些等用起来之后再单独设计。具体实现方式（应用内端到端加密，或借助 iCloud 等系统能力）也到那时再定。
- 需要提前知道的代价：忘记密码就无法恢复；加密内容在云端无法搜索，只能解锁后在本机搜索。
- 优先用于日记和备忘，因为它们最私密。
- 在此之前，密码等敏感内容不放进这个网站。

## 12. 测试

**自动测试**：业务规则写成纯 TypeScript 函数，用 Vitest 测试。

- **联动与排序**：重要日历事项出现在待办区，不重要的不出现；勾选来自日历的项目会写入对应事项；14 天范围；过期项目置顶且带标记；无日期待办排在组末；已完成默认隐藏；两种排序模式的结果；同优先级同日期时顺序稳定。
- **重复事项**：每天、每周几天、每月、每年的展开；每月 31 日在短月份跳过；跨夏令时变化后本地时间不变；`UNTIL` 和 `COUNT`；「仅这一次」的修改和删除；单次完成状态；重复事项不产生过期未完成。
- **删除**：删除进回收站、恢复；30 天清理后只剩墓碑；拉到墓碑后本机副本被清掉；对墓碑的过期修改不被应用且笔记内容存成冲突副本。
- **同步冲突**：`rev` 不一致时后到者胜，笔记和日记的旧正文被存成冲突副本且 `origin` 正确；副本不会再触发冲突；重复推送同一个 `op_id` 不产生副本；日记同日合并；例外同一次覆盖。
- **本机数据库**：清除本机数据后重新打开，云端数据完整下载，云端没有任何删除；游标和数据一起丢失、一起重建。
- **导出与导入**：导出的数据导入到一个空库后，所有导出字段与原数据完全一致，回收站里的记录仍在回收站；错误的 `format`、不支持的 `version`、非法 `id`、引用不存在的父记录，都被整体拒绝；云端已有且完整的 `id` 被跳过。
- **找回已清除的记录**：选项关闭时，墓碑被跳过；选项打开时，墓碑被还原，内容与备份一致，`purged_at` 被清除，`rev` 变大，另一台设备拉取后收到还原的内容；回收站状态的记录 `deleted_at` 被重置为导入时刻，当天的清理不会把它再清空；父记录先于子记录还原；日记日期被占用时跳过并列出。
- **搜索**：全角半角、大小写、多个词都要出现、不搜回收站。
- **出错分类**：本机写入失败、网络失败重试、服务器拒绝进入失败列表、会话过期后队列保留。

**手动检查清单**：每个阶段完成后，在真实的 iPhone（从主屏幕打开）和 Windows 浏览器各过一遍：登录、新建各类数据、离线修改后恢复联网、两台设备同时改同一条、导出并保存到「文件」或 iCloud 文件夹、导入、清除浏览器数据后重新打开。因为这两边的网页表现不一样。

## 14. 已知限制与前提

- **不能指望 Supabase 的备份**：官方文档没有写明免费版的备份保留或可下载备份。你的 JSON 导出就是唯一可靠的备份，所以有导出提醒。
- **免费项目可能被暂停**：官方文档写明，免费项目如果一周内几乎没有请求可能被暂停，每天正常使用不会触发，暂停前会提前发邮件。暂停后可以在控制台恢复。文档正文写恢复窗口是 1 年，但同一页里另有一处写 90 天，二者不一致，所以不要依赖这个窗口，以实际为准。暂停期间应用显示「云端暂时无法连接」，本机数据不受影响。
- **iPhone 的网页存储没有保证**：系统可能清理长期不用的网页存储，所以 IndexedDB 只是工作副本，靠写入后立即同步、未同步提示和定期导出来兜底。
